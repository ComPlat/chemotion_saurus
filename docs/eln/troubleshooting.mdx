## Chemotion ELN is not responding

In individual cases, it may happen that the Chemotion ELN does not react to an action. If the application appears to give no feedback, please reload the page by pressing <kbd>F5</kbd>. If the problem persists, please contact the team using the [helpdesk](https://chemotion.net/helpdesk).

## Actions are not activated

Check whether the active collection is a work collection. The **All Collection** tab is not intended for changes.

## Functions are not allowed

If the corresponding button for carrying out an action is not activated, it may be because the previous entries first have to be saved. This error occurs, for example, when editing a [sample](ui/elements/samples) in a [reaction](ui/elements/reactions) that has recently been inserted into the reaction table (by **split** or **copy**). If the new sample has not yet been saved in the reaction table, various functions are unavailable.

## Fixing Sample or Molecule SVG images

A script to reprocess the SVGs of molecules and samples is available (see [PR1308](https://github.com/ComPlat/chemotion_ELN/pull/1308/commits/868477dc91cec99b689db2ac93106d04ce8dd694)). For this to run properly, the [Ketcher backend service](../services/ketcher) has to be working. Note that depending on the situation, this could consume a lot of resources.
To run the script from the application directory with rails environment, use `bundle exec rake 'svg:{molecule|sample}[{all|missing|openbabel}]'`;
examples:

- reprocess missing molecule SVGs: `bundle exec rake svg:molecule`

- reprocess all molecule SVGs with molecule id &gt;= 200: `bundle exec rake 'svg:molecule[all, 200]'`

- reprocess missing sample SVGs with sample 100 &lt;= id &lt;= 200: `bundle exec rake 'svg:sample[missing, 100, 200]'`

- reprocess openbabel generated molecule SVGs: `bundle exec rake 'svg:molecule[openbabel]'`

If Docker Compose is used, the command can be run from the host where the `docker-compose.yml` file is located. For example, to run the command using the `worker` service:

```
docker compose exec worker bundle exec rake 'svg:molecule[openbabel]'
```

## Molecules are not imported correctly using CAS number

[Importing molecules into the ELN](ui/import) is supported e.g. using CAS numbers. In certain cases, the molecule generated with the CAS number is not displayed/stored correctly. In those cases, the structures contain additional protons in the displayed structure and the associated formula. E.g. known reported cases are K2CO3 or AgNO3. At the moment, the Chemotion team is not able to solve this issue as the information on the molecules is fetched from the CAS Common Chemistry API based on the CAS number. The explanation from CAS is cited here: 
"Salts derived from oxygen-containing acids are treated as multicomponent substances represented by dot-disconnect MF with the acidic hydrogens retained in the formula. This convention has often caused confusion in molecular formula searching since even a simple compound like sodium sulfate [7757-82-6] is assigned the CAS MF 'H2O4S.2Na' [...] The reason for this goes back to the earliest days of the Registry System in the mid-1960s. Print indexes were still the only means of access to Chemical Abstracts. This convention permitted all the salts of sulfuric acid to appear in one place in the Chemical Substance Index."
The only solution in those cases is to open and correct those molecules in the [chemical structure editor](ui/ketcher) manually.

## Docker setup and upgrades

### PostgreSQL collation version mismatch (`2.36` vs `2.41`) in `dbupgrade` logs

- **Symptoms**: When upgrading from version 3.x to version 4.x, the `dbupgrade` container logs show:
  ```text
  WARNING: database "postgres" has a collation version mismatch
  DETAIL: The database was created using collation version 2.36, but the operating system provides version 2.41.
  ```
- **Cause**: The version 4 database image uses a newer Debian base image with `glibc` `2.41` (compared to `2.36` in 3.x). When `dbupgrade` starts its temporary PostgreSQL server and connects to the `postgres` database to enumerate databases before running its post-upgrade maintenance loop, PostgreSQL emits this warning on that initial connection.
- **Solution**:
  - Check the end of the `dbupgrade` container logs using `./chemCLI instance log --service dbupgrade` (or `docker logs -f <instance>-dbupgrade-1`). Right after that initial connection, `dbupgrade` automatically runs `reindexdb` and `ALTER DATABASE ... REFRESH COLLATION VERSION` on `chemotion`, `postgres`, and `template1`, finishing with:
    ```text
    [POST-UPGRADE] chemotion: collation version 2.36 -> 2.41, reindexing
    [POST-UPGRADE] postgres: collation version 2.36 -> 2.41, reindexing
    [POST-UPGRADE] template1: collation version 2.36 -> 2.41, reindexing
    [POST-UPGRADE] done
    ```
    If `[POST-UPGRADE] done` is present, **`dbupgrade` has already resolved the mismatch** and no manual action is required.
  - If the log instead reports `[POST-UPGRADE] postmaster.pid present: a server is running on this data directory (or was not shut down cleanly), skipping.`, stop `db` cleanly and let `dbupgrade` run again:
    - For **ChemCLI-managed instances**:
      ```bash
      ./chemCLI off
      ./chemCLI on
      ```
    - For **manual Docker Compose installations**:
      ```bash
      docker compose stop -t 120 db
      docker compose up dbupgrade
      docker compose up -d db
      ```
  - If an older `dbupgrade` image was used without `[POST-UPGRADE]` output, upgrade to the latest `dbupgrade` image and re-run it, or manually refresh collations against `db` for `chemotion`, `postgres`, and `template1`:
    ```bash
    reindexdb -U postgres -d "$db"
    psql -U postgres -d "$db" -c "ALTER DATABASE \"$db\" REFRESH COLLATION VERSION;"
    ```

### ChemCLI download failures behind a proxy

- **Symptoms**: ChemCLI aborts during startup or instance creation with:
  ```sh
  <time> FTL Failed to download file from: https://github.com/Chemotion/ChemCLI/... Check log. ABORT!
  ```
  *(or from `https://raw.githubusercontent.com/Chemotion/ChemOrc/...`)*
- **Cause**: The host server requires an outbound HTTP/HTTPS proxy to reach external networks.
- **Solution**: Export proxy variables in your shell environment before calling ChemCLI:
  ```bash
  export HTTP_PROXY="http://proxy.dept.uni.de:<port>"
  export HTTPS_PROXY="http://proxy.dept.uni.de:<port>"
  ./chemCLI
  ```

### Containers stop automatically after closing the SSH session

- **Symptoms**: All Chemotion containers shut down gracefully (`Gracefully stopping...` / PostgreSQL `terminating connection due to administrator command`) shortly after the administrator logs out of their SSH session on the host.
- **Cause**: Docker is running under a user session (rootless Docker or user-scoped `systemd` service) where `systemd` user lingering is disabled (`loginctl show-user <user> -p Linger` returns `Linger=no`). When the last login session closes, `systemd` stops the user manager and terminates its processes.
- **Solution**: Enable `systemd` lingering for the user account on the host:
  ```bash
  sudo loginctl enable-linger <username>
  ```

## Accounts and authentication

### Account locked after failed login attempts

- **Symptoms**: A user cannot log in and reports their account has been locked.
- **Cause**: To protect against brute-force attacks, Chemotion ELN locks an account after 5 consecutive failed login attempts.
- **Solution**:
  - **Automatic unlock**: The lockout expires automatically after **10 minutes**, allowing the user to attempt login again.
  - **Administrative unlock**: An instance administrator can unlock the account immediately in [User management](admin/user-management) (**Administration → User Management**) or via ChemCLI:
    ```bash
    ./chemCLI instance user unlock --email jane.doe@dept.uni.de
    ```

## Exports, imports, and uploads

### Collection ZIP export does not download immediately

- **Symptoms**: After selecting collections in **Export collections** and clicking **Export ZIP**, the dialog closes without starting an immediate browser file download.
- **Cause**: Archiving collections and associated analytical data runs as an asynchronous background job on the `worker` container (`ExportCollectionsJob`).
- **Solution**:
  1. Check the **Notifications** bell icon on the **top left** navigation bar. When the export finishes, a notification appears with a direct link (**Download export archive**), which remains available for 24 hours.
  2. If outgoing email (SMTP) is enabled on your instance, an email containing the download link is also sent to the user.
  3. If the task fails or encounters an unreadable file on disk, inspect the `worker` container logs:
     ```bash
     ./chemCLI instance log --service worker
     ```
     *(Or `docker compose logs -f worker` for manual Docker Compose setups.)*

### Collection import fails when a reaction uses a sample from another collection

- **Symptoms**: Exporting a collection from one Chemotion ELN instance and importing it into another instance fails during import on a reaction.
- **Cause**: Collection export includes only the samples that belong to the exported collection(s), but every sample a reaction uses — starting material, reactant, solvent, purification solvent or product. If one of those samples belongs only to a collection that was not exported, the archive lacks that sample while the reaction still references it, and the import fails. Purification solvents are the most common case.
- **Solution**: Add the missing samples to the collection being exported (or export both collections together) before creating and importing the archive.

### File import fails silently (upload closes with no feedback)

- **Symptoms**: When uploading a large `.xlsx`, `.sdf`, or ZIP archive during import, the upload modal closes after a few seconds without showing errors or importing elements.
- **Cause**: Upstream reverse proxies (such as nginx or Apache) frequently enforce a default upload size limit (`client_max_body_size` defaults to `1m` in nginx), returning an HTTP 413 error before the request reaches the Rails application.
- **Solution**: In your reverse proxy configuration file (e.g. `/etc/nginx/conf.d/chemotion.conf`), increase the maximum body size:
  ```nginx
  client_max_body_size 100m;
  ```
  Reload the proxy service to apply the change (`nginx -s reload`).
